# Topic 2 · SBOM (Software Bill of Materials)

*Proving what is inside a container image.*

`satisfies: SBOM (SPDX) · SSDF "Produce Well-Secured Software" · ISO 27001 A.8.28 · CRA inventory`

---

## 1. What it is

An **SBOM** (Software Bill of Materials) is an **ingredients list** for a container image: every library and package baked inside it. Same idea as the ingredients label on food. You cannot judge whether something is safe if you do not know what is in it.

The payoff is concrete. When a dangerous bug is found in some library (think Log4Shell), the first question every company scrambles to answer is *"are we running it anywhere?"* Without an SBOM that is days of manual digging. With one it is a lookup. That is also exactly what the EU Cyber Resilience Act will require.

---

## 2. It is a signed attestation, not a loose file

An SBOM on its own is just a text file that anyone could edit. It becomes trustworthy when it is **attached to the image and signed**. That signed statement is called an **attestation**: a signed claim *about* an image.

Two pieces of vocabulary you will see in the output:

- **SPDX** is the *format* the ingredients list is written in (the other common one is CycloneDX).
- **in-toto** is the *envelope* the attestation is wrapped in. It has a `subject` (which image) and a `predicate` (the facts being attested, here the SBOM).

So verifying an SBOM does two things at once: it checks the signature is genuine, then hands you the contents.

---

## 3. Tools

- **cosign** (`verify-attestation`) to pull and verify the signed SBOM.
- **jq** to decode and read the JSON (`sudo apt install jq` if missing).
- The SBOM itself was generated by **`bom`** (sigs.k8s.io/bom), visible in the output as `Tool: bom-v0.7.1`.

---

## 4. How to verify (the plan)

Ask: *what is inside this image, and can I trust the list?*

```bash
cosign verify-attestation \
  --type spdxjson \
  --certificate-identity-regexp="https://github.com/metal3-io/.*" \
  --certificate-oidc-issuer="https://token.actions.githubusercontent.com" \
  quay.io/metal3-io/cluster-api-provider-metal3:v1.13.2 2>&1 | head -c 1500
```

What is different from Topic 1:

| Part | Meaning |
|---|---|
| `verify-attestation` (not `verify`) | "Give me the signed statement attached to the image," not just "is it signed?" |
| `--type spdxjson` | "The statement I want is the SBOM, in SPDX format." An image can carry several attestations, so you name which one. |
| strict identity + issuer flags | Same real trust check as Topic 1: only accept a metal3-io GitHub signer. |
| `\| head -c 1500` | The SBOM is large, so show only the first chunk. |

To actually read the package names, decode the attestation and pull them out:

```bash
cosign verify-attestation --type spdxjson \
  --certificate-identity-regexp="https://github.com/metal3-io/.*" \
  --certificate-oidc-issuer="https://token.actions.githubusercontent.com" \
  quay.io/metal3-io/cluster-api-provider-metal3:v1.13.2 2>/dev/null \
| jq -r '.payload | @base64d | fromjson | .predicate.packages[].name' | head -30
```

- `.payload` is **Base64**, which is *encoded, not encrypted*. `@base64d | fromjson` unpacks it into readable JSON.
- `.predicate.packages[].name` lists every package name in the ingredients list.

Count them:

```bash
... | jq -r '.payload | @base64d | fromjson | .predicate.packages | length'
```

## 5. Result (real output)

The names that came back:

```
base-files
netbase
tzdata
sha256:b02a7525f878e61fc1ef8a...
sha256:fcb6f6d2c9986d9cd6a2ea...
sha256:b12cc1cefc86f500e9dfb03b6b565a7f1ffef5177569730873f3ae43814275a1
... (more sha256 layer entries)
```

Two kinds of entries:

1. **Named OS packages**: `base-files`, `netbase`, `tzdata`. These are **Debian** packages, which tells you the image is built on a **Debian base**. These are the parts that receive CVEs and need patching, which is exactly why the SBOM matters.
2. **`sha256:...` entries**: image layers and components identified only by fingerprint, not a friendly name. One of them, `b12cc1...`, is the image's **own digest** (the same fingerprint from every signing step).

Total package count:

```
14
```

### The finding

CAPM3 is a Go service whose real dependency tree is dozens of Go modules (Cluster API, controller-runtime, Kubernetes client libraries, and their transitive deps), easily 100 to 200 packages. The SBOM lists **14**.

So the SBOM describes the **base OS layer** and **not the application's Go dependencies**. This is not a Metal3 mistake, it is a characteristic of how the SBOM is generated: `bom` was pointed at the **finished image**, so it sees what the OS package manager installed, but a compiled Go binary is opaque from the outside. The module list is baked into the binary and invisible unless the build feeds it in (for example generating from `go.mod` at build time, or using a Go-aware scanner like Syft).

**The gap:** CAPM3's published SBOM covers the base OS layer but not the Go dependency tree, which is the majority of the actual code. For CRA-style *"list everything in this and whether it is vulnerable"* that is a real limitation, and a possible small contribution (improve SBOM coverage), once confirmed it is not intentional.

---

## 6. The skill (why this matters)

The lesson is not "Metal3 has SBOMs." It is the habit: the pipeline **claims** an SBOM exists, and instead of accepting that, you opened it, counted, and found it thinner than it looks. Same move as Topic 1's loose-vs-strict identity check: **surface claim versus verified reality.** That instinct is the job.

It also sets up the arc of the plan: Metal3 has the *plumbing* (signing, attestation, SBOM attached) but the *depth* has gaps, SBOM coverage here and provenance missing entirely (Topic 3).

---

### One-line takeaway

> An SBOM is a signed ingredients list bound to a specific image. Reading it (not just confirming it exists) is what turns "we generate SBOMs" into "here is exactly what this image contains, and here is where the list stops short."
